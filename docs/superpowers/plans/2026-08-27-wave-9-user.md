# Wave 9: User, and turning the string columns into foreign keys

**Status:** Plan. No code written.
**Written:** 2026-08-27, after waves 1–8 landed.

---

## 1. Why this one is different

Every wave so far moved a model that pointed *at* User. This one moves User, and
that changes the character of the work twice over.

**It is the biggest by consumer count.** 80 files import the Mongoose model,
against 41 for Trip and GroupBooking combined. The heaviest are
`admin.service.ts` (27 sites), `dashboard.ts` (23), `auth.ts` (15) and
`bookings.service.ts` (14), then a long tail.

**It is the wave that makes the schema relational.** Every table migrated so far
holds user ids as bare `String` columns with nothing behind them:

```
trips.organizer_id            group_bookings.main_booker_id
wishlists.user_id             reviews.reviewer_id
follows.follower_id           posts.author_id
organizer_subscriptions.organizer_id   ... and roughly twenty more
```

Once User is a table, those become real foreign keys. That is the point of the
whole sequence, and it is also the step that can fail loudly: **any row pointing
at a user id that no longer exists will refuse to take the constraint.** That is
the check to run first, not last (see §5).

## 2. What is in the model

519 lines, six nested objects deep in places. The shape, and what each part
should become:

| Mongoose | Becomes | Why |
|---|---|---|
| scalars (email, name, role, phone, …) | columns | `email` unique, `role` an enum |
| `emergencyContact` (4 fields) | columns | fixed shape, always the same four |
| `socialLinks` (5 fields) | columns | same |
| `preferences` + `preferences.notifications` | columns + `String[]` | flat; the arrays stay arrays |
| `privacySettings` (4 fields) | columns | same |
| `idVerification` (8 fields) | columns | same |
| `organizerProfile` | columns | see below - it is the big one |
| `organizerProfile.qrCodes[]` | table | rows, with one active per method |
| `reputation.achievements[]` | table | rows |
| `verificationDocuments[]` | table | rows |
| `travelStats.reviewCount` / `averageRating` | **derived** | trigger, like trips |
| `socialStats` (3 counters) | **derived** | see §3 |
| `followers[]` / `following[]` | **deleted** | see §4 |
| `activityLog[]` | **deleted** | see §4 |

`organizerProfile` alone carries `businessInfo`, `bankDetails`, `autoPay`,
`trustScore` (with its own seven-field `breakdown`), plus a dozen scalars. It
flattens to roughly thirty columns. That is a lot, but they are all fixed-shape
and several are already queried by dotted path today - `organizerProfile.autoPay
.autoPayEnabled` and `organizerProfile.trustScore.overall` both appear in
filters, and a dotted path into a nested object is a column that has not been
written down yet.

Two of them do not flatten and should not: `bankDetails` duplicates what
`organizer_payout_configs` already stores properly (wave 7), and `autoPay`
overlaps `organizer_subscriptions`. Both need a decision before writing the
schema - see §6.

## 3. socialStats becomes derived, finally

`socialStats.followersCount`, `followingCount` and `postsCount` are stored
counters. Wave 1 deliberately kept them, and the note at the time said why: the
Follow rows had moved to Postgres but User was still in Mongo, so a Mongo-side
sort on `socialStats.followersCount` could not be replaced by a count of
Postgres rows.

That constraint disappears here. `follows` and `posts` are both Postgres tables,
so the counters become what they always claimed to be - and they get the same
treatment trips got: a trigger, so nothing can write one without the other
agreeing. The sort that kept them (`{ role: 1, 'socialStats.followersCount': -1 }`)
still needs a column, which is exactly the case a trigger-maintained counter is
for.

## 4. Two arrays to delete rather than port

**`followers[]` / `following[]`.** The Follow table replaced these in wave 1 and
nothing has written them since. One reader survives:
`recommendationService.ts:203` does `const followingIds = user.following || []`,
which has been an empty array for every user since wave 1 - so the
"people you follow also liked" half of recommendations has been silently
inert. It reads the follows table in this wave.

**`activityLog[]`.** Nothing writes it - not once in the codebase. But
`recommendationService.analyzeUserBehavior()` reads it to build the entire
preference model: viewed categories, liked categories, booked categories, price
range, preferred durations. All of it derived from an array that is always
empty, so `analyzeUserBehavior` has always returned empty maps and
recommendations have never been personalised at all.

There is already a `user_activities` table (wave 3) recording the same kind of
thing, written by real code paths. `analyzeUserBehavior` should read that.
That is a behaviour change - recommendations would start being personalised for
the first time - so it is called out here rather than slipped in.

## 5. Do the foreign key check first

Before writing a line of schema, find out whether the data can take the
constraints:

```sql
-- for each table holding a user id, how many point at nothing?
SELECT count(*) FROM trips t
  WHERE NOT EXISTS (SELECT 1 FROM users u WHERE u.id = t.organizer_id);
```

Except `users` does not exist yet, so on the migration run this is a check
against the Mongo user ids instead - a script that pulls every distinct user id
referenced by every Postgres table and asks Mongo which of them are real.

Production has 19 users and about 80 rows that reference one, so this is
seconds of work and can be verified by reading. It is still the first thing to
do, because the answer decides whether the FKs go on with `ON DELETE CASCADE`,
`ON DELETE SET NULL`, or not at all yet.

The three `_id`-on-a-Prisma-row bugs from wave 8 are a warning here too: the
typechecker cannot see through `any`, and most of these consumers pass users
around as `any`. Run `npm run typecheck:tests` as well as `npm run typecheck`.

## 6. Decisions needed before starting

1. **`organizerProfile.bankDetails` vs `organizer_payout_configs`.** Wave 7 gave
   bank details a proper home with an encrypted account number and an IFSC
   CHECK. The User copy is plaintext and unconstrained. Fold it in, or keep both?
2. **`organizerProfile.autoPay` vs `organizer_subscriptions`.** Same question.
   `autoPayService` reads the User copy; the subscription tables hold the
   payments.
3. **Does `analyzeUserBehavior` start reading `user_activities`?** Doing nothing
   keeps recommendations inert; doing it changes what users see.
4. **What happens to a user row when someone is deleted?** Today `deleteUser`
   removes the document and leaves their trips, bookings and reviews pointing at
   a missing id. With FKs that becomes an explicit choice.

## 7. Sequence

1. FK integrity check against production data (§5).
2. Prisma schema + migration: `users` plus `user_qr_codes`,
   `user_achievements`, `user_verification_documents`.
3. Constraints: email unique, role enum, the trust-score ranges, the
   one-active-QR-per-method partial index.
4. Triggers for `socialStats` and `travelStats` counters.
5. Port the 80 consumers, heaviest first.
6. **Then** the foreign keys, as their own migration, once every writer is on
   Postgres.
7. Delete `User.ts`. At that point nothing in `src/models` remains and the
   Mongo connection can come out of `index.ts`.

Step 6 is deliberately last and deliberately separate. Adding the constraints
while some code still writes users to Mongo would mean rows appearing in
Postgres with no matching parent.
